# 四天一轮协作流程

每位成员每轮至少完成一个有记录的实验，提交代码或诊断证据，并跟进至少一次实际比赛结果。失败、无提升、回退也可完成一轮，但必须说明依据。每轮的四个实验不等于必须替换四次正式计分版本。

## 四天节奏

- 第 1 天：看回放，选择一个具体问题，记录基线提交号、假设、指标和修改范围，避免同时改多项机制。
- 第 2–3 天：个人分支实现，基础检查，提交候选包；由发布负责人协调平台测试窗口，每个候选对应唯一代码提交。
- 第 4 天：完成比赛证据记录，另一人审阅，决定保留、回退或继续观察；补入报告，选出稳定候选。

平台若尚未产生结果，标记“等待比赛”，补写下一次跟进时间，不填虚构胜率。一次比赛用于确认能运行；有效性判断结合多局、地图、对手及过程指标。平台是否支持独立测试账号、固定种子或指定对手尚未确认，先按现有功能操作。

## 分支与审阅

`main` 保存可追溯的稳定版本。分支示例 `member-b/r02-fps-pathfinding`（Codex 创建的分支用 `codex/` 前缀）。从[首页](../README.md)指定的开发分支开始。交接代码合入后，从最新的 `main` 开分支。PR 必须链接实验文件和报告改动，由至少一名其他成员审阅后合并；这是团队约定，尚未配置服务器强制保护。

```bash
# 本轮交接代码在 codex/r01-local-evaluation
git fetch origin
git switch -c member-b/racing-braking origin/codex/r01-local-evaluation
# 编辑代码与实验记录后
git add strategies experiments report
git commit -m "R01: evaluate distance-aware braking"
git push -u origin HEAD
```

使用 GitHub 页面创建 PR。合并前解决冲突并重新检查。没提升的代码可以不合并，实验结论仍单独提交；不把失败记录删掉。共享报告按 Racing / FPS 小节划分编辑，同轮集成由轮值负责人处理。

## 平台发布协调

每轮只有一位发布负责人操作计分账号的版本切换。其他成员提交候选及清单，不互相覆盖。测试期间记录每次切换的开始和结束时间；比赛排队时核对结果关联的真实版本。测试结束恢复已确认的稳定版本，或正式采用经审阅的候选。
